# AC-Prof 实验执行

## 按需读取

初次运行查[快速开始](../../../README.md#快速开始)；规划矩阵查[采集协议与时间预算](../../../docs/Profiling_Protocol.md#结果行数和时间成本估算)。
仅当选用 profiler 时读[分析器](../../../docs/Profilers.md)；模型支持和镜像复用查[运行兼容](../../../docs/Runtime_Compatibility.md)。

## 执行流程

1. **固定本次实验问题。** 从用户已有要求确定模型/revision、设备、CPU/内存矩阵、输入尺度、batch、warmup/repeat、请求窗口、超时、profiler 和输出目录。缺少会改变实验含义的信息才澄清，不把完整默认矩阵当作一次快速验证。
2. **检查实时环境。** 按[实时状态入口](../../../docs/Troubleshooting.md#实时状态检查)读取必要状态，排查与本次资源冲突的活动采集。结合 CLI 权威预检确认环境和权限；不从旧元数据推断当前显存、磁盘、镜像或进程可用性。
3. **确定输入与成本。** 使用实际 workload/输入计划计算行数与时间；需要最大输入边界时使用独立 `probe.py`。探测、独立接口验证和正式 CSV 是不同产物，不混算样本或请求数。
4. **准备并执行。** 初次接口或环境变化先用独立目录做最小冒烟。根据已有授权运行目标矩阵，保留解析后的模型 commit、image ID、输入计划与日志；不同实验条件使用各自输出目录，不覆盖无关结果。
5. **跟踪生命周期。** 优先使用原采集日志和已有进度。不要为观察进度增加高频监控、额外 TUI 或 GPU 负载。遇到 OOM、超时或接口失败按[诊断分类](../../../docs/Troubleshooting.md#诊断证据)区分，保留部分产物和退出证据；不要盲目循环重跑或把失败行改成成功。
6. **验收并报告。** 命令结束后核对退出码、合并 CSV、实际计划覆盖、成功/预热/失败/剪枝行数及工具计划。任务还在运行时明确报告进度；成功写入几行不等于正式完成。完成后再按用户目标绘图或分析，报告参数、来源、产物位置和验证缺口。

`profile.py` 补采先用 `--dry-run` 检查所选工具和计划，实际补采沿用原 image ID、备份及来源记录。
启用某项工具表示允许采集该工具；本流程不会替用户添加 `--force-reprofile` 或删除历史结果。
